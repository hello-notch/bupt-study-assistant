# “邮学伴”Web 前端与 OneBot Bridge 设计方案

## 1. 产品定位

产品名为 **邮学伴**，副标题为“北邮人的学习与生活助手”。课程版不再把产品描述为 QQ 机器人，而是一套面向北邮学生的个人学习与校园信息管理软件；现有 NoneBot 服务层继续复用。

主要用户是学生，次要用户是系统管理员。课程版聚焦五项高频任务：

1. 查看今日课程和下一节课；
2. 管理 DDL 与提醒；
3. 查询校内通知、第二课堂活动；
4. 与学习助手对话，并让 AI 代办本人事务；
5. 管理订阅、隐私和提醒偏好。

## 2. 关键技术结论

### 2.1 前端能否直接代替 NapCat

可以保留现有 NoneBot 业务代码，但不建议让浏览器直接连接 NoneBot。浏览器无法可靠承担后台常驻、离线消息、文件路径转换、服务端密钥和 OneBot 动作响应等职责。

推荐新增一个独立的 **Web OneBot Bridge**：

```text
Vue Web / PWA
   │ HTTPS + WebSocket
   ▼
Web OneBot Bridge
   │ OneBot V11 反向 WebSocket
   ▼
现有 NoneBot 2（原有 matcher、service、repository）
```

Bridge 在 NoneBot 看来就是一个轻量版 NapCat：它向 `/onebot/v11/` 上报私聊消息事件，接收 `send_private_msg`、`send_msg`、`get_msg` 等动作，随后把结果推送给网页。这样聊天、命令、AI 工具、DDL、课程、校园查询和调度逻辑可以继续运行。

### 2.2 “零改业务代码”与原生界面的边界

- **兼容模式**：Bridge 把表单操作编译为 `/ddl ...`、`/course ...` 等文本命令。现有 NoneBot 可以完全不改，适合先打通链路和保留聊天界面。
- **课程成品模式（推荐）**：在 NoneBot 新增一个很薄的 `web_api` 接入插件，直接调用现有 service/repository，向任务页、课程页等返回结构化 JSON。原有业务模块不改，新增层只负责鉴权、参数转换和 DTO。
- 不建议长期解析机器人返回的中文文本来填充表格或日历；文案变化会使页面失效。

因此，建议把目标表述为：**不重写现有 NoneBot 业务逻辑；新增 Web 接入层。**

### 2.3 与 QQ 模式共存

课程期间使用 Bridge，课程结束后可把启动配置切回 NapCat。当前调度插件多处取 `get_bots()` 的第一个 Bot 发送通知，同时连接 NapCat 和 Bridge 时目标不确定，因此第一版采用“Web / QQ 二选一运行配置”，不要承诺双端同时在线。以后若要双端并行，只需补充通知渠道路由，不必重写业务功能。

## 3. 总体架构

### 3.1 组件

| 组件 | 推荐技术 | 职责 |
| --- | --- | --- |
| Web 前端 | Vue 3、TypeScript、Vite、Pinia、Vue Router | 页面、表单、日历、聊天、响应式布局 |
| Web OneBot Bridge | Python 3.12、FastAPI、WebSocket、Pydantic | 登录、会话、OneBot 事件/动作、消息队列、文件代理 |
| NoneBot | 保留现有项目 | matcher、AI、DDL、课程、校园服务、调度 |
| 数据 | 现有 SQLite + Bridge 独立 SQLite | 业务数据仍归 NoneBot；Bridge 只保存账号映射、会话和通知投递状态 |
| 离线能力 | PWA、Web Push（第二阶段） | 安装到桌面/手机、离线壳、系统通知 |

### 3.2 用户身份映射

现有代码大量把 `user_id` 转为整数传给 OneBot 动作，因此 Bridge 为每个 Web 用户分配一个稳定的纯数字 `onebot_user_id`。不要使用学号、邮箱或手机号作为 OneBot ID；Bridge 单独保存映射。

```text
web_user_uuid  <->  onebot_user_id  <->  data/users/<onebot_user_id>/
```

登录第一版使用本地账号和 Argon2id 密码哈希，Cookie 使用 HttpOnly、Secure、SameSite=Lax。不要收集或保存北邮统一认证密码。若以后接入学校统一认证，应单独完成合规与接口评估。

### 3.3 OneBot 最小兼容面

Bridge 第一阶段只实现当前 Web 场景实际需要的子集：

- 上报：`lifecycle.connect`、heartbeat、`message.private.friend`；
- 接收：`send_private_msg`、`send_msg`、`get_msg`、`get_login_info`、`get_status`；
- 消息段：`text`、`image`、`reply`，第二阶段增加 `file`；
- 每个动作必须按 `echo` 返回 OneBot V11 响应；
- `message_id`、`time`、`self_id`、`user_id` 均稳定且可追溯；
- NoneBot 发送的 `file://` 图片不能暴露给浏览器，Bridge 将其转换成带权限、短时有效的 `/media/<token>` 地址。

暂不实现群成员、戳一戳、表情回应、群历史、语音转写等 QQ 专属动作。未实现动作返回明确的 `retcode` 和错误信息，不能伪装成功。

## 4. 功能取舍

### 4.1 课程版保留并产品化

| 现有能力 | Web 产品中的位置 | 改造方式 |
| --- | --- | --- |
| DDL | “任务”页、首页摘要 | 原生表单、状态筛选、到期分组、提醒设置 |
| 课程表 | “课程”页、首页时间线 | 周视图、今日视图、导入向导、课程详情抽屉 |
| 信息门户 | “校园”页 | 通知列表、搜索、详情、订阅 |
| 第二课堂 | “校园”页 | 活动筛选、收藏/订阅；继续保持只读 |
| AI 聊天与工具 | “助手”页、全局快捷输入 | 对话、快捷问题、展示工具执行结果 |
| 计算器、Markdown | 助手内工具 | 不占一级导航 |
| 推荐 | 首页“现在做什么” | 只保留学习/休息建议，食物和歌曲降为可选 |
| 健康、日志、配额 | 管理后台 | 仅管理员可见 |
| 隐私、记忆 | 设置 | 数据分析开关、导出/删除申请、会话清理 |

### 4.2 从课程版移除或隐藏

- wife / marry / changewife / showwife；
- 群广播；
- 群水聊统计、群总结、群友语录；
- 主动插入群聊；
- 戳一戳、贴表情、QQ face；
- 群成员权限与按群功能开关；
- QQ 群回复、@、群头像和群名片依赖。

这些模块可继续保留在代码仓库，Web 运行配置不展示入口。切回 NapCat 时仍可恢复机器人特色。

## 5. 信息架构与导航

桌面端采用左侧导航，移动端采用底部五栏。普通用户只有五个一级入口：

1. **今天**：课程、DDL、校园动态和快捷提问的聚合首页；
2. **任务**：DDL 列表、创建、编辑、完成和提醒；
3. **课程**：周课表、今日课程、导入和提醒；
4. **校园**：信息门户通知与第二课堂活动；
5. **助手**：在线 AI 对话与本人事务代办。

右上角头像菜单包含通知中心、偏好设置、隐私与退出。管理员登录后额外出现 `/admin`，但不占普通用户主导航。

## 6. 关键页面设计

### 6.1 “今天”首页

首页不是统计仪表盘，而是一条从现在开始的行动流：

- 顶部显示日期、当前教学周和一句简短问候；
- 第一视觉焦点是“下一节课”，展示时间、地点、课程名和倒计时；
- 第二块是“近期任务”，按逾期、今天、三天内分组，可直接勾选完成；
- 第三块是“校园动态”，只显示 3 条与用户订阅相关的内容；
- 页面底部保留单行“问助手”输入框，支持“帮我安排今晚”“查奖学金通知”等自然语言入口。

空状态应给出明确下一步，例如“还没有课表，导入班级课表”，而不是空白卡片。

### 6.2 “任务”页

- 默认使用列表而非看板，更适合按截止时间扫描；
- 顶部有“全部 / 待完成 / 已完成”状态切换和搜索；
- 快速添加只要求“任务内容 + 截止时间”，提醒和备注放进展开项；
- 每条任务展示剩余时间、课程标签和提醒状态；
- 删除必须二次确认，完成可一键撤销；
- 支持自然语言录入，但提交前回显解析出的时间，避免误建 DDL。

### 6.3 “课程”页

- 桌面默认周视图，移动端默认今日时间线；
- 周视图的纵轴是节次/时间，横轴是周一到周日；
- 当前时段用细线标记，单双周和非本周课程降低强调；
- 点击课程打开详情抽屉，可编辑地点、教师、周次和提醒；
- “导入课表”采用三步向导：选择班级或文件 → 预览冲突 → 确认导入；
- 不把复杂命令参数暴露给用户。

### 6.4 “校园”页

- 页内只有“校内通知 / 第二课堂”两个标签；
- 统一搜索框，筛选器按数据源变化；
- 通知卡展示标题、来源、日期和已读状态；活动卡额外展示校区、类别、时间；
- 详情页打开原始来源，同时标明数据更新时间；
- 第二课堂严格保持查询和订阅，不提供报名、签到或退选按钮。

### 6.5 “助手”页

- 保持熟悉的消息流，但不模拟 QQ 界面；
- 右侧对话栏用于新建、切换和删除本地保存的独立对话，移动端改为横向对话列表；
- 首页快捷问题来自真实能力：“今天有什么课”“列出三天内 DDL”“最近有什么讲座”；
- 默认聊天模型为 `DeepSeek-V4-Flash-Vision-Exp`；模型声明支持时，发送按钮旁显示快速/思考切换；
- AI 调用工具时显示可读的过程状态，如“正在查询课表”，完成后以课程/任务卡呈现；
- 删除任务、覆盖课程等操作弹出确认；
- 图片上传仅在视觉能力启用时出现，限制为配置声明的 PNG/JPG/WebP，并在客户端和服务端同时校验；
- 助手统一使用“邮学伴”身份，不继承原机器人角色或人物关系。

### 6.6 设置与通知中心

- 通知中心聚合 DDL、课程和校园订阅，未读数只表达真实未读；
- 提醒设置支持默认提前量、静默时段和浏览器通知授权；
- 隐私页展示消息记录、AI 记忆/分析开关、数据导出与删除申请；
- 管理后台展示数据源健康、最近错误、AI 配额和备份状态，不向普通用户暴露内部地址或日志正文。

## 7. 视觉规范

- 气质：可靠、克制、校园感，不做 QQ 聊天气泡复刻；
- 主色：北邮语境下的深蓝/亮蓝，提醒使用琥珀色，危险操作使用红色；不直接使用学校标志，避免误导为官方产品；
- 字体：系统中文无衬线；数字、时间采用等宽数字特性；
- 圆角与阴影克制，课程和任务主要依赖层级、留白和状态标签区分；
- 同时支持浅色/深色；所有状态除颜色外还配图标或文字；
- 桌面内容最大宽度约 1200px，移动端最小支持 320px；点击区域不小于 44px；
- 关键操作必须有加载、成功、失败、空数据和离线五种状态。

## 8. 前后端接口建议

面向原生页面的 REST 接口采用 `/api/v1`，示例：

```text
GET    /api/v1/today
GET    /api/v1/tasks?status=todo
POST   /api/v1/tasks
PATCH  /api/v1/tasks/{id}
POST   /api/v1/tasks/{id}/complete
GET    /api/v1/courses/week?week=1
POST   /api/v1/courses/import/preview
POST   /api/v1/courses/import/{token}/confirm
GET    /api/v1/campus/notices
GET    /api/v1/campus/activities
GET    /api/v1/notifications
WS     /api/v1/chat
```

写操作统一返回 `trace_id`，供审计和故障定位。危险操作返回一次性确认 token。前端只处理展示和交互，不在浏览器复刻截止时间解析、课程冲突或权限规则。

## 9. 开发阶段

### 阶段 A：协议 PoC（3～4 天）

- Bridge 连接 `/onebot/v11/`；
- 浏览器发送纯文本，NoneBot 收到私聊事件；
- Bridge 正确响应 `send_private_msg` 和 `get_msg`；
- 验证 `/chat`、`/ddl list`、`/course today`、`/portal 5`。

若此阶段不稳定，不进入 UI 大规模开发。

### 阶段 B：课程 MVP（1～2 周）

- 账号、会话、WebSocket 重连和消息持久化；
- 完成应用外壳、“今天”“任务”“课程”“助手”；
- 增加薄 `web_api` 接入层，停止解析自然语言列表；
- 完成任务和课程的主要增删改查。

### 阶段 C：校园与提醒（1 周）

- 校园通知、第二课堂页面；
- 通知中心、离线待投递和浏览器通知；
- 导入向导和冲突预览。

### 阶段 D：工程化与答辩（1 周）

- 权限、审计、错误页、空状态、响应式适配；
- 单元测试、OneBot 合约测试、端到端测试；
- 部署脚本、演示数据、需求/设计/测试文档；
- 演示“同一套 NoneBot 业务在 Web Bridge 与 NapCat 间切换”。

## 10. 验收标准

- 浏览器的一条消息能以合法 OneBot 私聊事件进入现有 matcher，回复可实时返回；
- DDL、课表和订阅写入仍由现有 service/repository 完成，重启后不丢失；
- 网页关闭时提醒先进入待投递队列，重新打开后可见且不重复；
- Bridge 不泄露本机 `file://` 路径、Cookie、API key 或运行日志；
- 手机与桌面均可完成“添加 DDL—收到提醒—标记完成”的闭环；
- Web 模式不依赖 QQ 或 NapCat，QQ 模式可通过启动配置恢复；
- 未实现的 OneBot 动作有明确失败响应；
- 课程答辩可以展示需求、架构、数据库、接口、测试和部署，而不只是聊天机器人界面。
