# 邮学伴客户端与服务端改进设计方案

## 1. 设计目标

本方案面向将“邮学伴”从课程项目和本地 Web 页面进一步封装为可分发软件。目标是：

- 用户首次启动即可注册、登录和使用，不要求手工粘贴 Cookie 或配置文件；
- 服务端统一提供模型请求转发，以及信息门户、教务系统、第二课堂的只读校园数据；
- 任务、课程、对话、设置和大部分用户数据优先保存在客户端；
- 校园凭据、模型 API Key 和用户密码不泄露到浏览器、不进入日志或 Git；
- 不再把 NoneBot 作为 Web 产品的必需后端；
- 在数据源失效、网络中断、模型额度不足时，给出可理解且可恢复的状态。

本方案不实现第二课堂报名、签到、退选，也不绕过验证码、二次验证、访问控制或学校系统风控。

## 2. 当前框架与改造依据

当前项目事实来源如下：

| 现有部分 | 当前职责 | 改造判断 |
| --- | --- | --- |
| `web/` | Vue 3、TypeScript、Vite 前端，包含首页、任务、课程、校园和助手页面 | 作为桌面客户端 UI 的基础 |
| `web/dev-api.ts` | 当前本地 API，代理 AI、门户通知、教务课表、第二课堂和电费查询 | 拆分为正式服务端 API；保留接口语义，去除开发服务器耦合 |
| `src/amadeus_bot/services/` | 课程、DDL、校园访问、AI 路由、渲染等业务服务 | 将与 OneBot 无关的规则迁移到客户端或服务端领域层 |
| `src/amadeus_bot/plugins/` | NoneBot matcher、QQ 消息处理和机器人命令 | 不作为新 Web/桌面运行时依赖 |
| `config/ai_routes.toml` | 当前 AI 供应商、模型和能力配置 | 迁移为服务端模型路由配置 |
| `secrets/` | 当前本地 API Key、校园 Cookie、校园密码和 token | 不直接复制到发布包；改用服务端密钥库或客户端系统密钥库 |
| `localStorage` | 当前保存任务、课程、设置、对话等数据 | MVP 可兼容迁移，正式桌面版逐步迁移到本地 SQLite/IndexedDB |

当前校园自动登录由 Playwright 和 `scripts/refresh_web_campus_session.py` 完成。新架构应保留“检测失效、触发官方登录、成功后重试一次”的行为，但不把现有个人密码文件直接部署到公共服务器。

## 3. 总体架构

```text
┌──────────────────────────────┐
│ 邮学伴客户端                  │
│ Vue 3 UI + 桌面壳 + 本地存储  │
│ 任务/课程/对话/设置/通知缓存   │
└───────────────┬──────────────┘
                │ HTTPS（在线登录后访问）
                ▼
┌──────────────────────────────┐
│ 邮学伴服务端                  │
│ 用户认证与会话                │
│ 模型 API 网关                 │
│ 校园数据网关                  │
│ 缓存、限流、健康检查、审计     │
└──────────┬───────────┬───────┘
           │           │
           ▼           ▼
   模型供应商 API   信息门户/教务/第二课堂
```

桌面壳可以选择 Tauri 或 Electron。Python 业务不必全部重写：可将现有 Python 解析器和定时任务编译为本地 sidecar；服务端则使用独立的 HTTP API 服务。NoneBot/OneBot 作为可选的 QQ 兼容模式单独启动，不进入普通客户端的主链路。

## 4. 客户端设计

### 4.1 欢迎、注册与登录

欢迎界面增加注册和登录入口。这里的账号是“邮学伴账号”，不等同于北邮统一认证账号。

- 注册使用昵称加密码，不添加邮箱或手机号，无验证。具体字段可按实际产品决定；
- 客户端只通过 HTTPS 提交密码，服务端只保存 Argon2id 或同等级算法的密码哈希；
- 登录成功后获得短期 Access Token 和可撤销的 Refresh Token；
- Refresh Token 使用 HttpOnly、安全 Cookie 或系统安全存储，不放进普通 `localStorage`；
- 支持退出当前设备、查看登录设备和撤销全部会话；
- 未登录时可展示欢迎页和本地静态功能，但在线 AI 与校园数据明确显示为需要登录。

### 4.2 本地数据

以下数据默认只保存在客户端：

- DDL、课程表、课程提醒和本地导入文件；
- AI 对话、已读状态、助手设置和个性化记忆；
- 校园通知、第二课堂活动的本地缓存；
- 用户昵称、头像、主题和提醒偏好。

当前 `localStorage` 可以作为 Web 兼容层，但正式桌面版建议使用本地 SQLite 或 IndexedDB，以便支持大对话、图片、索引、迁移和事务。任何校园密码、Cookie、Refresh Token、模型 Key 都不得写入 `localStorage`。

客户端应提供：

- 数据导出；
- 清空对话和缓存；
- 注销本机；
- 选择是否把对话发送到服务端模型；
- 网络、校园数据和模型服务的独立状态提示。

### 4.3 校园数据使用方式

客户端通过服务端校园数据网关获取：

- 信息门户通知；
- 教务系统的只读课表或班级课表；
- 第二课堂活动列表和订阅信息。

但必须给每类数据定义范围：

- 真正公共或全校相同的数据，可以由服务端使用授权的公共会话抓取、缓存后提供；
- 与个人身份相关的成绩、个人课表、报名记录等，不应使用开发者个人账号代查。若学校没有正式的用户授权接口，应在客户端通过官方登录完成查询，或暂不提供该功能；
- 服务器返回的数据必须带 `source`、`fetchedAt`、`status` 和原始 `url`，区分在线、缓存、成功空结果、鉴权失败和网络失败。

### 4.4 凭据失效体验

客户端不让用户复制 Cookie。若服务端向学校官网数据请求失败，则提供缓存数据，但告知客户端这是服务器缓存数据。
若客户端向服务端数据请求失败，则显示客户端自身缓存数据，同样说明这是客户端缓存数据。

## 5. 服务端设计

### 5.1 用户认证服务

服务端保存邮学伴账号信息和密码哈希，不保存明文密码。建议数据表包括：

- `users`：用户 ID、昵称、密码哈希、创建时间、状态；
- `sessions`：设备、Refresh Token 哈希、过期时间、撤销时间；
- `consents`：隐私、模型转发和校园数据使用同意记录；
- `audit_events`：登录、注销、密钥变更和异常事件，不记录密码、Cookie 和完整请求正文。

### 5.2 模型 API 网关

模型请求全部由服务端发起，供应商 API Key 只保存在服务端密钥管理系统中，不下发给客户端。

网关职责：

- 按 `config/ai_routes.toml` 或数据库配置选择供应商和模型；
- 对客户端参数重新校验，不能信任浏览器传来的模型、MIME、大小和思考参数；
- 支持流式响应、超时、重试、限流和备用模型；
- 区分 Key 无效、余额不足、请求超限、模型不存在和供应商故障；
- 对日志和错误信息脱敏；
- 按用户或设备统计额度，防止公共 Key 被滥用。

客户端不要求填写 API Key。后续可以增加“自带 Key”高级模式，但 Key 应保存在客户端系统密钥库，并由服务端仅接收请求，不在普通页面显示。

### 5.3 校园数据网关

校园网关作为独立模块，不嵌入 NoneBot matcher。建议接口：

```text
GET  /api/v1/campus/notices
GET  /api/v1/campus/notices/{id}
GET  /api/v1/campus/activities
GET  /api/v1/campus/courses?classId=...
GET  /api/v1/campus/status
POST /api/v1/campus/session/renew
```

每个数据源使用独立适配器，包含登录入口、健康检查、解析器、限流和错误分类。服务端应缓存公共数据，避免每个客户端请求都直接触发学校网站访问。

校园适配器不得把 Cookie、Authorization Token 或统一认证密码返回给客户端。管理端只展示数据源健康状态和错误摘要，不展示凭据正文。

### 5.4 本地数据同步策略

默认采用“本地优先”：

- 任务、课程、对话等写入本地；
- 服务端只保存账户、设备会话、必要的配额和订阅元数据；
- 用户主动开启同步时，再上传经过授权的数据；
- 同步数据使用用户 ID 隔离，删除账户时按策略删除服务端副本。

## 6. NoneBot 的取舍

新产品运行时不依赖 NoneBot。现有代码可以分为三类：

| 现有模块 | 新架构处理 |
| --- | --- |
| 课程解析、DDL 规则、校园解析、AI 路由、Markdown 渲染 | 抽取为普通 Python domain/service，供 HTTP API 或本地 sidecar 使用 |
| `chat`、`calc`、`courses`、`ddl` 等面向 QQ 的 matcher | 不作为主界面入口；需要 QQ 模式时放入兼容包 |
| `wife`、群广播、群聊统计、群总结、群友语录、戳一戳、贴表情、群成员权限、QQ 日志 | 新产品删除或不加载 |
| `runtime_logging`、`health`、部分权限逻辑 | 改造成服务端日志、健康检查和 Web 权限中间件 |
| OneBot/NapCat Bridge | 作为可选 QQ 插件，不和客户端登录、校园数据、模型网关耦合 |

迁移时先抽取无协议依赖的服务，再删除 Web 运行配置中不需要的插件。不要让前端为了调用课程或任务而构造 `/ddl`、`/course` 等机器人命令，也不要长期解析机器人中文回复来填充页面。

## 7. 安全要求

- 全部外部通信除信息门户均使用 HTTPS；开发环境和不支持HTTPS的信息门户才允许本机 HTTP；
- Access Token 短期有效，Refresh Token 可撤销并只保存哈希；
- 服务端凭据使用环境外的密钥管理或受保护文件，禁止提交 `.env`、`secrets/`、Cookie、Token 和数据库；
- 所有上游错误经过白名单化处理，禁止把完整 HTML、响应头或 Cookie 返回浏览器；
- 对模型请求设置输入长度、图片数量、MIME 和大小上限；
- 对校园源设置并发上限、指数退避和缓存；
- 账号、请求、设备和本地缓存按用户作用域隔离；
- 清楚告知用户哪些内容会发送到模型服务端，以及缓存保存多久；
- 遵守校园系统使用条款，不共享个人账号，不绕过验证码或访问控制。

## 8. 实施阶段

### 阶段一：客户端登录和模型网关

- 欢迎页、注册、登录、退出和设备会话；
- 将当前 `/api/assistant/chat`、标题生成和能力配置迁移到正式服务端；
- 服务端密钥库和限流；
- 保持现有助手页面和本地会话结构。

### 阶段二：校园数据网关

- 把 `/api/campus`、`/api/campus/summary`、`/api/courses/class` 拆成版本化接口；
- 加入数据源健康状态、缓存和错误分类；
- 先上线信息门户和公共第二课堂数据；
- 再评估个人教务数据是否具备合法、稳定的授权方式。

### 阶段三：桌面封装和本地存储迁移

- Tauri/Electron 外壳、托盘和自动更新；
- Python sidecar 或独立本地服务；
- 从 `localStorage` 迁移到 SQLite/IndexedDB；
- 提供数据导出、清理和本机注销。

### 阶段四：可选 QQ 兼容模式

- 单独打包 NoneBot/OneBot Bridge；
- 只加载仍有价值的聊天、提醒和工具功能；
- 普通桌面客户端不安装或不启动 NapCat。

## 9. 验收标准

- 新用户只需注册邮学伴账号即可进入软件，不需要填写模型 API Key；
- API Key 不出现在客户端、浏览器存储、日志和错误提示中；
- 校园数据能区分在线、缓存、空结果、鉴权失败和网络失败；
- 校园会话失效时可以从客户端一键进入官方登录流程，并在成功后恢复任务；
- 任务、课程、对话和设置在客户端重启后仍然存在；
- 服务端无法通过共享开发者个人账号返回其他人的个性化数据；
- NoneBot 未启动时，Web/桌面核心功能仍可用；
- 删除或禁用 QQ 相关插件后，客户端主流程不受影响。
